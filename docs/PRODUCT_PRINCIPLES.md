# 产品原则

## 1. 产品定位

Agent Tech Radar 是一个可由个人积累、团队共享的技术知识调研与沉淀系统，不是新闻聚合器或通用爬虫平台。

> 以 AI 会话探索与被动知识雷达为双重输入，以证据和实验持续校验，构建可由个人积累、团队共享的技术知识调研与沉淀的图谱。

它希望解决的核心问题是：

> 在技术快速变化的情况下，如何既承接人通过 AI 会话发起的主动探索，又通过被动雷达持续发现人没有问到的技术与变化，并把重要认识变成可查源、可质疑、可修正、可共享的长期资产？

## 2. 两条信息流

### AI 会话探索流

起点是个人或团队成员在 AI 会话中的真实问题：某个框架值不值用、某个结论可不可信、两个方案有什么取舍。系统保留提问、回答、质疑、追问和认知修正过程，而不只保存最后一段总结。Codex 是当前的首个会话集成，不是概念上唯一的 AI 会话来源。

### 被动知识雷达流

在用户没有主动提问时，系统仍通过可审计的查询族、官方 API、包注册表、发布 Feed、官方组织列表和论文索引，持续发现尚未被关注的候选以及既有技术的重要变化。

两条流最终在“还缺什么证据”上交汇。

## 3. 知识的最小单位

会话原文不是最终知识单位。系统应该把它提炼为可独立理解的对象：

- 概念：一个值得长期保留的理解。
- 问题：尚未回答或值得继续调查的空白。
- 质疑：对现有认识的反例、条件或可疑之处。
- 回答：对某个问题的当前回应，不默认等于真理。
- 结论：经证据或实验支持、经人审核后可用于技术决策的断言。
- 决策：在具体约束下对技术的 `watch / assess / trial / adopt / hold` 判断。

每个对象都应尽量具有来源、时间、查证状态、置信度和与其他对象的关系。

## 4. 认知来源与事实证据分离

这是整个系统最重要的数据边界。

- AI 会话是 provenance：它记录某个问题为什么被提出、某个理解如何形成和如何变化。
- 官方文档、官方仓库、标准、论文、发布记录和可重复实验是 evidence：它们支持或反驳外部技术断言。
- AI 的总结、评分和推断必须显式标注，不与源事实混在一起。
- 当证据冲突时，保留双方并将结论标记为 `contested`，而不是强行选择一个答案。

## 5. 从对话到结论的晋级阶梯

```text
会话来源
  → 学习笔记（可待查证）
  → 调研问题 / 实验假设
  → 证据或实验结果
  → 变更提案
  → 人工审核
  → 正式结论 / 技术决策
```

AI 可以在每一级提出建议，但不能跳过证据和审核将对话答案直接变成已认定事实。

## 6. 图谱的视觉语义

- 图上的技术候选必须与至少一条技术路线连接，避免用审核状态把图谱拆成两套没有语义关系的群落。
- 节点大小表达规模和热度信号，不表达产品评分。
- 颜色、边框和虚实用于表达节点类型、审核状态和证据状态，不应让用户靠猜。
- 结论较长时，图上显示可识别的摘要，完整内容放在详情面板。
- 图谱必须支持从任意节点发起追问，并将新的会话学习结果连回原节点。

## 7. AI 会话与长期调研 Agent

AI 会话是主动探索、查源、实验和修改执行的一条核心入口，Codex 是当前首个集成。网页的作用是组织上下文、生成可审查的任务交接和展示结果，不在后台偷偷代替用户对话。被动知识雷达是与之并列的另一条核心入口，不属于会话的附属功能。

对于未来的长周期调研，系统可以借鉴 Prime Agent 一类 Harness 的思路：

- 持久目标、任务脱离界面后继续执行以及中断后恢复。
- 将大规模资料保存为可编程的外部状态，将子调查交给隔离的子 Agent。
- 从运行轨迹中复盘有效策略，但经验的持久化必须有证据、版本、适用范围和回滚能力。
- 子 Agent 的输出仍然是待检查材料，不因并行数量多就自动获得更高置信度。

执行 Harness 应当可替换：Agent Tech Radar 管理知识、证据和审核，不把核心数据锁定在任何一个 Agent 产品中。

## 8. 明确不做什么

- 不自建通用网页爬虫。
- 不将 Star、Fork、搜索排名或社交媒体热度当作技术质量证明。
- 不追求不可证明的“已搜尽全网”。
- 不让 AI 在无审核情况下改写历史结论、实验结果或审核记录。
- 不为了图更大而堆积无关节点。
- 不把当前 Demo 宣传成已经可以无人值守运行的生产系统。
